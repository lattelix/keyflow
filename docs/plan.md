# Исполняемый план

## Алгоритм выбора работы
1. Проверить живой repository/file; прочитать `AGENTS.md` и `docs/STATE.md`.
2. Запустить `python3 tools/plan.py validate`. Ошибка структуры плана — блокер, а не повод продолжать наугад.
3. Запустить `python3 tools/plan.py next`. Команда выбирает первую по порядку задачу со статусом `planned`, завершёнными зависимостями и пройденными воротами. Для конкретной роли: `--role designer`, `--role engineer`, `--role reviewer` или `--role product`.
4. Прочитать карточку и только её входные спецификации. Сверить доступные возможности инструментов с требуемыми.
5. До работы зафиксировать task ID, branch, base SHA, затрагиваемые Figma узлы и список результатов. Один активный исполнитель на единицу изменений.
6. Выполнить шаги по порядку. Проверить каждый пункт `checks`; сохранить доказательства.
7. Передать `needs_review`. Ревьюер проверяет результат независимо; только затем задача становится `done`.
8. Обновить STATE, очередь и handoff. Новую задачу начинать только в рамках явного продолжения пользователем или установленного задания агенту.

Без shell применяется тот же алгоритм вручную; отсутствие инструмента нельзя маскировать словом «проверено».

## Приоритеты
Сначала достоверный inventory и спецификация, затем foundations и компонентный UX, затем реальный прототип и принятие дизайна. Только после `G-IMPLEMENT`: toolchain, проверка рисков, минимальная инфраструктура разработки и implementation. Нельзя неделю совершенствовать каталог, пока не работает один законченный обучающий маршрут.

## Что обязано быть в карточке
ID, роль, этап, зависимости, ворота, цель, требования, входные файлы, разрешённые пути/страницы, пошаговые действия, выходные артефакты, проверка, условие остановки. Очередь — источник истины карточек; не дублировать статусы в нескольких несогласованных списках.

## Управление изменениями
Новая фича → требование → decision/ADR при изменении архитектуры → экран/состояние → задача → тест. Не наоборот. При уточнении контракта сначала обновить спецификацию и тестовые ожидания в одном review, затем писать код.

Если задача слишком велика для одного PR или одного надёжного контекста, разделить её на дочерние карточки с новыми ID. Сохранить исходную цель и внешние зависимости; валидатор не должен увидеть цикл. Отчёт о разделении требует review, но не разрешает увеличить scope.

## Проверяемый результат текущего этапа
Новая модель без истории чата должна определить первую задачу, найти её входы и критерии, не выдумывая стек/музыку/доступы. Это проверяется чтением с чистого контекста и валидатором связей. Качество дизайна и обучения проверяется отдельно, не этим скриптом.
