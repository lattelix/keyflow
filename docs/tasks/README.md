# Как читать и изменять очередь

Карточки разделены для небольшого контекста модели:

| Файл | Карточки | Назначение |
|---|---|---|
| [01-design.json](01-design.json) | KF-001–KF-016 | Inventory, foundations, компоненты,16экранов и prototype handoff |
| [02-web.json](02-web.json) | KF-017–KF-037 | Проверочные spikes, web alpha с обучением, QA и отдельно разрешённый pilot |
| [03-expansion.json](03-expansion.json) | KF-038–KF-050 | MIDI, native; затем только предложения sync/advanced/desktop за своими gates |

[queue.json](queue.json) содержит порядок файлов и **единственное место хранения статусов**. Определения задачи и её текущее выполнение не смешиваются: карточка говорит «что надо сделать», запись `states` — «что действительно сделано».

## Обычная работа
Из root: `python3 tools/plan.py validate`, затем `python3 tools/plan.py next`, затем при необходимости `python3 tools/plan.py show KF-001`. `next --role designer` фильтрует по роли, но не обходит product/review dependency. Если текущая задача in_progress или needs_review, сначала завершить/проверить её.

Команды только читают файлы. Они не меняют статусы, не пишут Figma, не вызывают модели, не создают branches/deployments и не выдают себе разрешений.

## Переход статуса
`planned → in_progress → needs_review → done`. При проблеме `blocked` с полем `reason`; отложенная задача `deferred`. Перед началом все depends_on должны быть done, gates — passed. У needs_review нужен существующий report/evidence. У done дополнительно reviewer. Сам факт записи reviewer name не доказывает независимость: она проверяется по report/реальным действиям.

После работы исполнитель обновляет только свою запись `states`, сохраняет report, затем запускает validate. Ревьюер заполняет verdict/evidence и меняет done только после фактической проверки. При одобрении этапа gate содержит approved_by, approved_at ISO и evidence; отсутствие ответа владельца не считается согласием.

## Чего не делает validator
Не скачивает внешние ссылки для подтверждения approvals, не смотрит Figma, не слушает музыку, не измеряет игру и не проверяет, что человек действительно reviewer. Он ловит структурные ошибки и очевидные обходы порядка. Для содержательной приёмки есть отдельный [reviewer guide](../operations/reviewer.md).

## Большая задача
Карточки задают ограниченные результаты этапа. Если её нельзя выполнить надёжно за один PR/контекст, сначала добавить дочерние карточки с уникальными ID, явными dependencies и acceptance; согласовать разбиение, сохранив scope. Не превращать «разделил задачу» в разрешение строить новую фичу или backend.

Будущие неизвестные решения находятся в spikes/ADR, а не в выдуманных SDK versions. Task outputs могут ещё не существовать; task inputs в текущей спецификации должны существовать и быть прочитаны. После завершения dependency обязательно прочитать её actual report и outputs перед использованием API.
